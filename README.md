# شهروند مدنی | Citizen Madani

سامانه جامعه دیجیتال کارکنان بیمارستان مدنی. رابط کاربری با React، TypeScript و Vite ساخته شده و برای احراز هویت و داده‌های پایدار از Supabase استفاده می‌کند.

## امکانات پیاده‌سازی‌شده
- ورود کارکنان با ایمیل و رمز عبور از طریق Supabase Auth
- نمایش فهرست کارکنان فعال پس از ورود
- ثبت درخواست تبادل بخش یا بیمارستان
- مشاهده درخواست‌های ثبت‌شده و وضعیت آن‌ها
- اطلاعیه‌های بیمارستان با امکان ذخیره پیش‌نویس و انتشار توسط مدیران
- پیام‌رسان خصوصی دونفره کارکنان با وضعیت خوانده‌شدن پیام‌ها
- پنل مدیریت کارکنان با جست‌وجوی نام/سمت/بخش، فیلتر وضعیت، آمار فعال/غیرفعال، ویرایش مشخصات و کنترل وضعیت توسط مدیر مجاز
- سجل فقط‌خواندنی رویدادهای مدیریتی برای تغییر پرونده کارکنان، بررسی درخواست‌ها، انتشار اطلاعیه‌ها و تصمیم‌های جابه‌جایی شیفت
- برنامه شیفت کارکنان با ثبت شیفت صبح/عصر/شب، تخصیص توسط مدیر و درخواست جابه‌جایی دو شیفت با تأیید مدیر؛ تأیید درخواست، تخصیص کارکنان دو شیفت را در یک تراکنش جابه‌جا می‌کند؛ حتی برای دو شیفت هم‌نوع و هم‌تاریخ، با قفل‌گذاری مرتب و کنترل یکتاییِ به‌تعویق‌افتاده
- تقویم ماهانه شیفت‌ها با حرکت بین ماه‌ها، نمایش تعداد و نوع شیفت هر روز و خروجی CSV سازگار با Excel با پشتیبانی از متن فارسی
- گزارش تحلیلی شیفت‌ها شامل فیلتر بخش/نوع/کارمند، روند شش‌ماهه، مقایسه ماه جاری با ماه قبل، توزیع بار کاری کارکنان و خروجی CSV و Excel
- پیام‌رسان با پیوست خصوصی حداکثر پنج فایل و مجموع حجم ۱۰ مگابایت برای هر پیام
- بازارچه و آگهی‌های کارکنان شامل فروش کالای دست‌دوم، معرفی خدمات، محصولات و درخواست جابه‌جایی بخش؛ آگهی‌ها ابتدا در صف بررسی قرار می‌گیرند و فقط پس از تأیید مدیر برای کارکنان نمایش داده می‌شوند.
- پنل مدیریت آگهی‌ها برای تأیید، رد و بستن آگهی؛ کارکنان نیز می‌توانند آگهی خود را ببندند و آگهی‌های منقضی‌شده از فهرست عمومی حذف می‌شوند.
- اطلاعیه‌های عمومی حقوق، کارانه، اضافه‌کاری و مزایا با ذخیره پیش‌نویس، انتشار و بازگرداندن به پیش‌نویس توسط مدیران؛ کارکنان فقط اطلاعیه‌های منتشرشده را مشاهده می‌کنند.
- امور رفاهی شامل قراردادهای طرف قرارداد، تخفیف‌ها و شرایط اقساطی با دسته‌بندی، اطلاعات تماس و تاریخ اعتبار.
- ثبت خطا و تجربه به‌صورت متن یا صوت، همراه با پیگیری و پاسخ مدیر؛ رابط کاربری هشدار می‌دهد که اطلاعات قابل شناسایی بیماران ثبت نشود.
- سیاست‌های Row Level Security و محدودسازی مجوزهای سطح جدول و ستون

## راه‌اندازی محلی
1. وابستگی‌ها را نصب کنید: `npm install`
2. فایل `.env.example` را به `.env.local` کپی کنید.
3. مقادیر `VITE_SUPABASE_URL` و `VITE_SUPABASE_PUBLISHABLE_KEY` را از پروژه Supabase خود وارد کنید.
4. همه Migrationها را دقیقاً به‌ترتیب زمانی اجرا کنید: `202611200001_initial_schema.sql`، `20261121000000_employee_portal.sql`، `20261121010000_manager_review.sql`، `20261121020000_announcements.sql`، `20261121030000_direct_messages.sql`، `20261121100000_employee_management.sql`، `20261121110000_harden_table_grants.sql`، `20261121120000_active_account_access.sql`، `20261121130000_admin_audit_log.sql`، `20261121140000_work_shifts_and_swaps.sql`، `20261121150000_private_message_attachments.sql`، `20261121160000_sender_message_deletion.sql`، `20261121173000_multi_message_attachments.sql`، `20261121180000_multi_attachment_storage_rls.sql` و `20261121190000_shift_swap_audit.sql` و `20261121200000_active_employee_storage_access.sql` و `20261121210000_safe_shift_swap_constraint.sql` و `20261121220000_employee_notifications.sql` و `20261121230000_staff_community_and_compensation.sql` و `20261122000000_staff_welfare_partners.sql` و `20261122010000_staff_reports_and_audio.sql`.
5. برنامه را اجرا کنید: `npm run dev`

## ایجاد حساب کارکنان
حساب‌ها باید توسط مسئول مجاز سامانه در Supabase ایجاد یا دعوت شوند. ثبت‌نام عمومی را در تنظیمات Auth غیرفعال نگه دارید. پس از ایجاد حساب، trigger پایگاه داده یک پروفایل اولیه می‌سازد. مسئول سامانه باید نام نمایشی، کد پرسنلی، سمت و بخش را از مسیر امن و مورد تأیید سازمان تکمیل کند.

## امنیت و محدودیت‌های فعلی
- برنامه شیفت برای کارکنان فعال قابل مشاهده است؛ فقط مدیر فعال امکان ایجاد، ویرایش و حذف برنامه را دارد. درخواست جابه‌جایی فقط برای شیفت متعلق به درخواست‌دهنده و شیفت همکار دیگر پذیرفته می‌شود؛ تغییر تخصیص فقط در Trigger پایگاه داده و هنگام تأیید مدیر انجام می‌شود.
- رویدادهای مدیریتی با Triggerهای پایگاه داده ثبت می‌شوند؛ کاربران مرورگر مجوز درج یا ویرایش گزارش‌ها را ندارند و مشاهده گزارش فقط از طریق سیاست مدیر فعال ممکن است. گزارش شامل نوع رویداد و فیلدهای تغییرکرده است، نه متن پیام‌ها یا توضیحات خصوصی درخواست‌ها.
- کلید publishable/anon فقط در مرورگر استفاده می‌شود؛ هرگز کلید `service_role` را در متغیرهای `VITE_*` یا کد سمت کاربر قرار ندهید.
- سیاست‌های RLS اجازه می‌دهند هر کارمند فقط درخواست‌های خودش و پیام‌هایی را که فرستنده یا گیرنده آن است بخواند.
- پیام‌رسان خصوصی است؛ ارسال پیام فقط با هویت فرستنده واردشده انجام می‌شود و گیرنده فقط می‌تواند وضعیت `read_at` را تغییر دهد.
- پیوست پیام‌ها در Storage خصوصی با محدودیت نوع فایل و حجم ۱۰ مگابایت برای هر پیام نگهداری می‌شوند؛ حداکثر پنج فایل و مجموع حجم حداکثر ۱۰ مگابایت است. مالکیت و دسترسی هر فایل جداگانه بررسی می‌شود و خواندن فقط برای طرفین پیامِ دارای حساب فعال مجاز است؛ غیرفعال‌شدن حساب، دسترسی Storage به پیوست‌ها و حذف فایل‌های یتیم را نیز مسدود می‌کند. حذف پیام توسط فرستنده به‌صورت نرم انجام می‌شود و همه پیوست‌ها از پیام جدا می‌شوند.
- مجوزهای جدول‌ها به‌صورت حداقلی بازتنظیم شده‌اند؛ مدیر فقط می‌تواند فیلدهای پرسنلی مجاز را تغییر دهد و نقش مدیریتی از رابط کاربری قابل ارتقا نیست.
- حساب غیرفعال در سطح RLS از فهرست کارکنان، درخواست‌ها، اطلاعیه‌های منتشرشده و پیام‌های خصوصی عملیاتی محروم می‌شود؛ پروفایل پایه خودش برای نمایش پیام وضعیت باقی می‌ماند.
- تست‌های خودکار مخزن، ترتیب Migrationها، کنترل‌های امنیت پیوست‌ها، ثبت رویدادهای جابه‌جایی شیفت، محدودیت دسترسی Storage برای حساب‌های غیرفعال و ایمنی جابه‌جایی هم‌زمان شیفت‌ها را بررسی می‌کنند. این تست‌های ایستا جایگزین اجرای Migrationها و آزمون RLS واقعی در Supabase نیستند.
- فضای جامعه کارکنان برای آگهی تبلیغاتی، خریدوفروش کالای کارکرده، آگهی جابه‌جایی بخش و بازارچه محصولات کارکنان (ثبت آگهی با وضعیت در انتظار تأیید مدیر)
- بخش اخبار حقوق، کارانه و اضافه‌کاری با انتشار اطلاعیه‌های تأییدشده توسط مدیران.
- ثبت خطا و تجربه کارکنان به‌صورت متن و فایل صوتی اختیاری، با پیگیری وضعیت و پاسخ مدیر؛ گزارش‌ها خصوصی هستند و فقط ثبت‌کننده و مدیر مجاز آن‌ها را می‌بینند. فایل صوتی در Storage خصوصی با محدودیت حجم ۱۰ مگابایت ذخیره می‌شود.
- امور رفاهی با فهرست قراردادهای معتبر مجموعه‌های طرف قرارداد (ورزش و تفریح، خرید، غذا، سلامت، سفر، آموزش و خدمات)، نمایش تخفیف یا شرایط اقساطی، اطلاعات تماس و بازه اعتبار؛ فقط مدیران قراردادها را منتشر می‌کنند و کارکنان فعال پیشنهادهای معتبر را می‌بینند.
- مرکز اعلان‌ها از جدول `employee_notifications` استفاده می‌کند. اعلان پیام خصوصی، تغییر وضعیت درخواست‌ها و انتشار اطلاعیه توسط triggerهای دیتابیس ساخته می‌شود؛ RLS دسترسی هر کارمند را به اعلان‌های خودش محدود می‌کند. وضعیت خوانده‌شدن با Realtime همگام می‌شود.
- پیش از استفاده عملیاتی، تنظیمات Auth، محدودیت ایمیل سازمانی، پشتیبان‌گیری، نگهداری داده‌ها و دسترسی‌های مدیریتی باید توسط مسئول فناوری اطلاعات بیمارستان بازبینی شوند.

## راه‌اندازی مدیر سامانه
پس از ایجاد حساب مدیر و تکمیل احراز هویت او، شناسه UUID همان کاربر را از Supabase Auth دریافت و با SQL Editor نقش او را ارتقا دهید:

```sql
update public.employee_profiles
set role = 'admin'
where id = '<AUTH_USER_UUID>';
```

این کار را فقط برای کارکنان مورد اعتماد و پس از تأیید هویت انجام دهید. نقش مدیر از سمت مرورگر قابل تغییر نیست. مدیران می‌توانند درخواست‌ها را ببینند و وضعیت آن‌ها را تأیید یا رد کنند؛ کارکنان عادی فقط درخواست‌های خود را می‌بینند.

## ساخت و انتشار نسخه وب
1. در تنظیمات محیطی سرویس میزبانی، دو متغیر زیر را با مقادیر پروژه Supabase ثبت کنید:
   - `VITE_SUPABASE_URL`
   - `VITE_SUPABASE_PUBLISHABLE_KEY`
2. دستور ساخت را روی `npm run build` قرار دهید.
3. پوشه خروجی انتشار `dist` است.
4. پس از هر انتشار، ورود، فهرست کارکنان، ثبت درخواست، اطلاعیه‌ها و پیام‌رسان را با حساب‌های آزمایشی کارمند و مدیر بررسی کنید.

این پروژه هنوز به سرویس میزبانی خاصی متصل نشده است. ساخت موفق GitHub Actions به معنی انتشار آنلاین یا اجرای Migrationها در Supabase نیست.

## آزمون یکپارچه دیتابیس محلی
برای اجرای واقعی Migrationها و تست PostgreSQL، Docker و Supabase CLI لازم است:

1. نصب Supabase CLI مطابق مستندات رسمی
2. اجرای `supabase start`
3. اجرای `supabase db reset` برای ساخت دیتابیس تمیز و اعمال همه Migrationها
4. اجرای `supabase db lint --fail-on error` برای بررسی خطاهای توابع و ساختار PostgreSQL
5. اجرای `supabase db advisors --type security --fail-on error` برای بررسی ایرادهای امنیتی سطح خطا
6. اجرای `supabase test db` برای آزمون جابه‌جایی واقعی دو شیفت هم‌نوع و بررسی Constraint و هویت مدیر
7. در پایان اجرای `supabase stop --no-backup`

GitHub Actions این مراحل را در job جداگانه `database-integration` اجرا می‌کند؛ lint و security advisor در CI فقط در سطح خطا باعث شکست job می‌شوند. این آزمون‌ها روی دیتابیس محلی و موقت CI هستند و هیچ تغییری در پروژه Supabase عملیاتی ایجاد نمی‌کنند.

## دستورات
- `npm run dev` — اجرای محیط توسعه
- `npm test` — اجرای تست‌های خودکار کنترل Migration و امنیت پیوست‌ها
- `npm run build` — بررسی TypeScript و ساخت نسخه انتشار
- `npm run preview` — پیش‌نمایش نسخه ساخته‌شده
- `supabase db reset` — بازسازی دیتابیس محلی و اجرای Migrationها
- `supabase test db` — اجرای تست‌های یکپارچه PostgreSQL
